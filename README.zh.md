# 🔒 P2P Chat — 无后端的端到端加密聊天

[🇬🇧 English](README.md) · [🇪🇸 Español](README.es.md) · [🇩🇪 Deutsch](README.de.md) · [🇨🇳 中文](README.zh.md) · [🇷🇺 Русский](README.ru.md)

> 一个完全在浏览器中运行的点对点（P2P）端到端加密聊天应用。没有服务器,没有账号,任何人的设备上都不会留下日志。只需打开页面、分享一个房间名,即可开始聊天。

---
## 这是什么?

**P2P Chat** 是一个单页网页应用,让两个或更多人可以聊天、传输文件、并验证彼此的身份——**完全不依赖任何后端**。没有中心服务器、没有数据库、没有用户账号、也没有遥测数据。

浏览器本身就是客户端。WebRTC 负责点对点连接。Web Crypto(运行在 Web Worker 中)负责加密。IndexedDB 在本地存储你的聊天记录。你在界面上看到的一切,都源自这三大基石。

它是一个渐进式网页应用(PWA):你可以像原生应用一样将它安装到手机或电脑上,界面在离线状态下也能使用。

---
## 为什么要做这个?

大多数所谓"私密"的聊天应用仍然要求你信任服务器的运营方。即使他们声称有端到端加密,他们依然知道谁在什么时候和谁聊天。这个项目彻底把服务器从这个等式中移除:

- **没有后端可被查封、传唤或攻破。**
- **无需注册账号。**
- **在你无法掌控的基础设施上不留任何元数据痕迹**(信令层除外,见下文说明)。
- **你可以自己托管**——GitHub Pages、Cloudflare Pages、Netlify,甚至一个 U 盘都行,因为它只是静态文件。

---

## 功能特性

### 核心功能
- 基于 WebRTC 数据通道的**点对点聊天**。
- **可选的端到端加密**,使用 AES-GCM(256 位),密钥通过 PBKDF2(20 万次迭代,SHA-256)从共享密码派生。
- **每 24 小时自动轮换密钥**——旧的消息密钥会过期;新密钥基于同一密码、以轮转的时间槽重新派生。
- **多个房间、多个标签页**——可同时打开并管理多个对话。
- **持久化聊天记录**,存储在 IndexedDB 中(按房间、按设备)。
- **消息队列**——发给离线联系人的消息会先在本地保存,等对方重新上线后再送达。
- **送达回执**——✓ 已发送,✓✓ 已送达。
- **远程删除消息**——可以只在本地删除,也可以为所有拥有该消息的人删除。
- **文件与图片传输**——通过同一条加密数据通道分块传输。
- **可选择不保存文件到聊天记录**(仅保留文件名)。

### 安全与身份验证
- **带外(out-of-band)SAS 校验**——基于 ECDH(P-256)密钥交换派生出的 6 位数字码,用于确认不存在中间人攻击。
- **可选的 PIN 锁**,支持因不活动而自动锁定。
- 界面中显示**指纹信息**,方便联系人在首次接触时验证你的身份。
- 本地存储的**联系人列表**。

### 使用体验
- **可安装的 PWA**,带离线界面外壳。
- **多语言界面**:西班牙语、英语、德语、中文、俄语。
- **深色 / 浅色 / 跟随系统**三种主题,以及**三种字体大小**。
- **虚拟滚动**——可流畅处理成千上万条消息。
- **网络统计信息**——已发送/接收的字节数、往返延迟(RTT)、连接类型(直连或中继)。
- **内部日志**,可按类别(连接、ICE、消息)筛选。
- **诊断面板**,显示完整的内部状态以便排查问题。
- **重新连接操作**——重启连接、清除信令缓存、彻底重置。

## 使用方法

1. 打开已部署的网址(或在本地运行,见下文)。
2. 点击 **＋** 创建一个聊天。
3. 选择一个**房间名**,并可选地设置一个**密码**。
   - 不设密码:连接依然是加密的(DTLS),但没有额外的 E2E 加密层。
   - 设置密码:会额外添加一层 AES-GCM 加密,并且信令消息(SDP)也会被加密,防止在信令层发生中间人攻击。
4. 通过*另一条*安全渠道,将房间名(以及密码)分享给你的联系人。
5. 开始聊天。文件可以拖入窗口,也可以通过 📎 附加。

### 验证身份

连接建立后,在状态栏点击联系人 → **查看 SAS**。通过另一条独立渠道(当面、Signal、电话)与对方核对这 6 位数字码。如果一致,点击**保存并验证**。

## 工作原理

```
┌────────────────┐                          ┌────────────────┐
│   浏览器 A       │                          │   浏览器 B       │
│                 │                          │                 │
│  ┌──────────┐   │                          │  ┌──────────┐   │
│  │ P2P Chat │   │◄────────────────────────►│  │ P2P Chat │   │
│  └──────────┘   │      WebRTC (DTLS)       │  └──────────┘   │
│     ▲     ▲     │                          │     ▲     ▲     │
│     │     │      │                          │     │     │      │
│   界面   加密     │                          │   界面   加密     │
│         Worker  │                          │         Worker  │
└────┬────────────┘                          └───────────┬────┘
     │                                                    │
     └────────────► 信令 ◄───────────────────────────────┘
          (BitTorrent 追踪器 / Nostr / MQTT)
```

1. **信令**:两个浏览器通过一个公开的去中心化网络互相发现——默认使用 BitTorrent 追踪器,并以 Nostr 和 MQTT 作为备用方案。如果设置了密码,SDP 消息(其中包含 DTLS 指纹)在发送前会先被加密,这样恶意的信令节点就无法实施中间人攻击。
2. **连接**:WebRTC 协商建立直接的点对点连接。如果网络阻断了直连路径(例如双方都处于 CGNAT 后面),流量会通过 TURN 服务器中继——依然是端到端加密的,只是延迟更高。
3. **加密**:WebRTC 始终使用 DTLS-SRTP 加密。如果你设置了密码,数据通道*内部*会再叠加一层 AES-GCM 加密,且密钥每 24 小时轮换一次。
4. **存储**:消息和文件在本地以 IndexedDB 存储;如果设置了密码,静态存储数据也会被加密。
5. **持久化**:重新加载页面时,应用会恢复你的房间并自动重新连接。

## 安全与隐私

**受到保护的内容:**
- 消息内容(始终有 DTLS;设置密码后还有 AES-GCM)。
- 信令内容(SDP),前提是设置了密码。
- 文件(与消息相同)。
- 本地静态存储的聊天记录(前提是设置了密码)。

**未受保护的内容:**
- 在直连情况下,**你的 IP 地址对联系人可见**。这是 WebRTC 的固有特性。如果连接通过中继(TURN),你的联系人看到的是中继服务器的 IP,但 TURN 运营方能看到你的真实 IP。
- **信令层**(BitTorrent 追踪器、Nostr 中继、MQTT 代理)能看到有两个 IP 正在尝试建立连接,除非你设置了密码(此时它无法读取 SDP 内容,但仍能看到连接尝试本身)。
- 除 DTLS 本身提供的保护外,**没有额外的前向保密性**。如果攻击者同时获取了你的密码*和*你的 IndexedDB,就能解密当前密钥时间槽(24 小时窗口)内存储的消息。

**威胁模型**:这个应用旨在防御被动的网络监控,以及想要读取你聊天内容的服务运营方。它*并非*设计用来防御已被攻破的设备、拥有流量关联能力的全局攻击者,或是故意泄露你聊天内容的联系人。

**建议:**
- 始终设置一个强随机密码。
- 通过另一条渠道分享密码(Signal、当面告知)。
- 验证 SAS 码。
- 如果不想让联系人看到你的 IP,请使用 VPN。

---

## 局限性

- **在部分网络环境下需要中继(TURN)**(约 15%–20% 的连接,尤其是移动网络/CGNAT 环境)。应用默认使用免费的公共 TURN 服务器,这类服务是尽力而为的,可能较慢。
- **不支持离线送达**:如果发消息时对方离线,消息会在本地排队,等对方重新连接后送达。没有服务器为对方保留消息。
- **标签页关闭后没有推送通知**。桌面通知只有在页面在后台保持打开时才有效。
- **不支持多设备同步**:每台设备都有各自独立的聊天记录。没有服务器的情况下,无法在手机和电脑之间同步。
- **本地存储有限制**:浏览器在移动端通常将 IndexedDB 限制在约 50MB。大文件会很快占满空间;如果不需要保留文件,请关闭"保存文件到聊天记录"。
- **信令层是公开的**:追踪器和中继属于共享基础设施。如果它们宕机,应用就无法找到联系人。可以尝试其他策略(Nostr、MQTT),或自行搭建 coturn 服务。

## 部署方式

### GitHub Pages(推荐)

1. 克隆或 fork 本仓库。
2. 确保以下文件位于根目录:`index.html`、`app.js`、`i18n.js`、`sw.js`、`manifest.json`、`icon.svg`,以及 `modules/` 文件夹。
3. 在 **Settings → Pages → Source: main branch / root** 中启用 GitHub Pages。
4. 完成。HTTPS 由 GitHub 提供。

### 任意静态托管平台

由于没有后端,任何静态托管都可以使用:Cloudflare Pages、Netlify、Vercel、普通的 nginx、S3 存储桶,甚至用 `python -m http.server` 搭在树莓派上。

### 本地开发

```bash
# 任何静态服务器都可以。例如:
python3 -m http.server 8080
# 然后打开 http://localhost:8080
```

> 重要提示:crypto.subtle、navigator.clipboard、通知功能和 Service Worker 都需要 HTTPS 或 localhost 环境。以 file:// 方式打开 index.html 会导致部分功能无法使用。

## 模块
modules/ 目录下的三个文件(crypto.worker.js 除外)都是通过 esbuild 从 Trystero 打包而来。如果你想重新构建它们:
```bash
npm install --save-dev trystero@0.21.6 esbuild
mkdir -p modules
for strat in torrent nostr mqtt; do
  echo "export * from 'trystero/$strat'" > .entry.js
  npx esbuild .entry.js --bundle --format=esm --target=es2022 \
    --platform=browser --outfile=modules/trystero-$strat.js
done
rm .entry.js
rm -rf node_modules package.json package-lock.json
```

## 技术栈
- 原生 JavaScript(ES 模块),不依赖框架。
- WebRTC 负责点对点传输。
- Trystero 负责基于 BitTorrent、Nostr 和 MQTT 的信令。
- Web Crypto API(运行在 Web Worker 中)负责 AES-GCM、PBKDF2、ECDH、SHA-256。
- IndexedDB 负责本地持久化存储。
- Service Worker 负责 PWA 离线界面外壳。
- 应用本身无需任何构建步骤。
